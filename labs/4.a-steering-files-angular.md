## Understanding Steering Files

Steering files are Markdown files with a YAML front matter block that the agent reads on every invocation. The front matter controls when the file is applied.

```
---
inclusion: always
---
```

There are three inclusion modes:

| Mode | When the file is read |
|---|---|
| `always` | On every single agent interaction |
| `fileMatch: "src/**/*.ts"` | Only when the agent is working on TypeScript files in src/ |
| `manual` | Only when explicitly referenced with `#filename` |

For this lab, all three steering files use `always` — they apply globally.

> ### ⚠️ Front matter syntax — Amazon Q vs Kiro
>
> Older Amazon Q documentation shows the front matter key as `alwaysApply: true`.
> **Kiro uses `inclusion: always` instead.** Using the old syntax means the file will
> not be activated automatically.
>
> ```markdown
> # ❌ Old Amazon Q syntax — does NOT work in Kiro
> ---
> alwaysApply: true
> ---
>
> # ✅ Correct Kiro syntax
> ---
> inclusion: always
> ---
> ```
>
> If your verification prompts (Step 6) return wrong answers, check this first.

````markdown
# Architecture Standards

## Tech Stack

This project uses the following technology stack. Do not suggest alternatives
unless explicitly asked.

| Layer | Technology | Version |
|---|---|---|
| Language | TypeScript | 5.x (strict mode) |
| Framework | Angular | 17+ (standalone components) |
| UI Components | Angular Material | 17+ |
| HTTP | Angular HttpClient | Built-in |
| Routing | Angular Router | Built-in |
| Forms | Angular Reactive Forms | Built-in |
| Testing (unit) | Jest + Angular Testing Library | Latest |
| Testing (e2e) | Cypress | Latest |
| Styling | SCSS | Per-component encapsulation |
| Build | Angular CLI | 17+ |
| Linting | ESLint + angular-eslint | Latest |

## Project Structure

Follow strict feature-based architecture. Every feature must have its own folder
with all associated files co-located:

```
src/
  app/
    core/                        ← Singleton services, guards, interceptors
      services/
      guards/
      interceptors/
    shared/                      ← Reusable components, pipes, directives
      components/
      pipes/
      directives/
    features/
      [feature-name]/            ← One folder per feature
        components/              ← Smart and presentational components
        services/                ← Feature-scoped services
        models/                  ← Interfaces and types for this feature
        [feature-name].routes.ts ← Lazy-loaded route config
    app.component.ts
    app.config.ts                ← Root application config (standalone)
    app.routes.ts                ← Top-level route definitions
  environments/
    environment.ts
    environment.prod.ts
```

## Component Rules

- All components must be **standalone** — never use NgModules
- Use `OnPush` change detection on every component
- Separate smart (container) components from presentational (dumb) components
- Smart components handle data fetching and state; presentational components receive
  data via `@Input()` and emit events via `@Output()`
- Use Angular Signals for local component state where possible

## Approved Libraries

Only use libraries from this list. Do not add new dependencies without
discussion. If you need something not on this list, say so and explain why.

- `@angular/core` — Framework core
- `@angular/common/http` — HttpClient for API calls
- `@angular/router` — Routing
- `@angular/forms` — Reactive Forms
- `@angular/material` — UI component library
- `@angular/cdk` — Component Dev Kit (used by Material)
- `rxjs` — Reactive programming (operators only — no custom Subjects in templates)
- `@testing-library/angular` — Component testing utilities
- `@testing-library/user-event` — User interaction simulation in tests
- `jest` — Unit test runner
- `cypress` — End-to-end testing

## Forbidden Patterns

Never use these patterns — if you see them in existing code, flag them:

- ❌ NgModules — this project uses standalone components exclusively
- ❌ `ngOnInit` for data fetching in presentational components — use smart components
- ❌ `any` type in TypeScript — always use explicit types or generics
- ❌ Direct DOM manipulation (`document.getElementById`, `ElementRef.nativeElement`) — use Angular bindings
- ❌ `Default` change detection — always use `ChangeDetectionStrategy.OnPush`
- ❌ Inline styles on components — use SCSS files with component encapsulation
- ❌ Subscribing inside a subscribe — use `switchMap`, `mergeMap`, or other RxJS operators
- ❌ Unmanaged subscriptions — always use `takeUntilDestroyed()` or the `async` pipe
- ❌ `console.log` in production code — remove all debug statements before committing
- ❌ Hardcoded API URLs — always use `environment.ts` variables
````

## Step 3 — Create testing-standards.md

Create `.kiro/steering/testing-standards.md`:

```bash
touch .kiro/steering/testing-standards.md
```

Add the following content:

````markdown
---
inclusion: always
---

# Testing Standards

## Test Pyramid

Every feature must have tests at all three levels:

1. **Unit tests** — test services and pure functions in isolation with Jest
2. **Component tests** — test component behaviour with Angular Testing Library
3. **E2E tests** — test critical user journeys with Cypress

Aim for: 60% unit tests, 30% component tests, 10% E2E tests.

## Naming Convention

All test files must be co-located with the file they test and use the `.spec.ts` suffix:

```
user.service.ts
user.service.spec.ts

user-card.component.ts
user-card.component.spec.ts
```

All test descriptions must follow this pattern:

```
describe('[ClassName]', () => {
  describe('[methodName or scenario]', () => {
    it('[expected behaviour]', ...)
  })
})
```

Examples:
```typescript
describe('UserService', () => {
  describe('getById', () => {
    it('returns the user when found', ...)
    it('throws NotFoundException when user does not exist', ...)
  })
})

describe('UserCardComponent', () => {
  it('displays the user full name', ...)
  it('emits deleteUser event when delete button is clicked', ...)
})
```

Do not use vague descriptions like `it('works')` or `it('test 1')`.

## AAA Pattern

Every test must follow the Arrange-Act-Assert pattern with blank lines between
sections and comments marking each section:

```typescript
it('displays the user full name', async () => {
  // Arrange
  const user: User = {
    id: 1,
    firstName: 'Jane',
    lastName: 'Smith',
    email: 'jane@example.com',
  };

  await render(UserCardComponent, {
    componentInputs: { user },
  });

  // Act — (no action needed for render-only assertions)

  // Assert
  expect(screen.getByText('Jane Smith')).toBeInTheDocument();
});
```

```typescript
it('emits deleteUser event when delete button is clicked', async () => {
  // Arrange
  const user: User = { id: 1, firstName: 'Jane', lastName: 'Smith', email: 'jane@example.com' };
  const deleteHandler = jest.fn();

  await render(UserCardComponent, {
    componentInputs: { user },
    componentOutputs: { deleteUser: { emit: deleteHandler } as any },
  });

  // Act
  await userEvent.click(screen.getByRole('button', { name: /delete/i }));

  // Assert
  expect(deleteHandler).toHaveBeenCalledWith(1);
});
```

## Service Testing Rules

- Always use `TestBed` with `provideHttpClientTesting()` for services that use HttpClient
- Mock all dependencies with `jest.fn()` — never use real HTTP calls in unit tests
- Use `HttpTestingController` to assert HTTP requests and flush mock responses
- Test one behaviour per `it` block — do not assert multiple unrelated things

Standard service test setup:

```typescript
describe('UserService', () => {
  let service: UserService;
  let httpMock: HttpTestingController;

  beforeEach(() => {
    TestBed.configureTestingModule({
      providers: [
        UserService,
        provideHttpClient(),
        provideHttpClientTesting(),
      ],
    });

    service = TestBed.inject(UserService);
    httpMock = TestBed.inject(HttpTestingController);
  });

  afterEach(() => {
    httpMock.verify();
  });

  it('fetches a user by id', () => {
    // Arrange
    const mockUser: User = { id: 1, firstName: 'Jane', lastName: 'Smith', email: 'jane@example.com' };

    // Act
    let result: User | undefined;
    service.getById(1).subscribe(user => (result = user));

    // Assert
    const req = httpMock.expectOne('/api/v1/users/1');
    expect(req.request.method).toBe('GET');
    req.flush(mockUser);
    expect(result).toEqual(mockUser);
  });
});
```

## Component Testing Rules

- Always use `@testing-library/angular` — do not use `fixture.debugElement` queries
- Query elements by accessible role, label, or text — never by CSS class or test ID
- Use `userEvent` from `@testing-library/user-event` for simulating interactions
- Never test implementation details (internal methods, private properties)

## Test Data

- Never use production data in tests
- Use realistic but fake data (real-looking names, valid email formats)
- Define shared test fixtures in a `__fixtures__` folder alongside the spec file
- Do not share mutable state between test cases — recreate fixtures in `beforeEach`
````

````markdown
# API Design Standards

## HttpClient Rules

All HTTP calls must go through a dedicated feature service — never call HttpClient
directly from a component.

- One service per API resource (e.g. `UserService`, `ProductService`)
- All services must be provided in root: `@Injectable({ providedIn: 'root' })`
- Always return `Observable<T>` — never subscribe inside a service
- Use strongly typed generics: `this.http.get<User[]>(...)` — never use `any`

## Base URL

All API calls must use the base URL from the environment file — never hardcode URLs:

```typescript
// ✅ Correct
import { environment } from '../../../environments/environment';

@Injectable({ providedIn: 'root' })
export class UserService {
  private readonly baseUrl = `${environment.apiUrl}/users`;
}

// ❌ Wrong
private readonly baseUrl = 'http://localhost:8080/api/v1/users';
```

Environment files:

```typescript
// environment.ts
export const environment = {
  production: false,
  apiUrl: 'http://localhost:8080/api/v1',
};

// environment.prod.ts
export const environment = {
  production: true,
  apiUrl: 'https://api.yourapp.com/api/v1',
};
```

## URL Conventions

Match the backend REST conventions exactly:

| Operation | Method + URL |
|---|---|
| List all | `GET /api/v1/users` |
| Get by ID | `GET /api/v1/users/{id}` |
| Create | `POST /api/v1/users` |
| Full update | `PUT /api/v1/users/{id}` |
| Partial update | `PATCH /api/v1/users/{id}` |
| Delete | `DELETE /api/v1/users/{id}` |

Resource names are **plural nouns** — never verbs, never camelCase in URLs.

## Request and Response Models

Define explicit TypeScript interfaces for every request and response — never use `any`
or raw `object`.

```typescript
// models/user.model.ts
export interface User {
  id: number;
  firstName: string;
  lastName: string;
  email: string;
  createdAt: string; // ISO 8601
}

export interface CreateUserRequest {
  firstName: string;
  lastName: string;
  email: string;
  password: string;
}

export interface UpdateUserRequest {
  firstName?: string;
  lastName?: string;
}
```

## Error Handling

All HTTP errors must be handled via a global `HttpInterceptor` — do not catch errors
individually in each service.

Standard error interceptor pattern:

```typescript
export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  return next(req).pipe(
    catchError((error: HttpErrorResponse) => {
      switch (error.status) {
        case 400:
          // handle validation errors — extract error.error.errors[]
          break;
        case 401:
          // redirect to login
          break;
        case 403:
          // redirect to forbidden page
          break;
        case 404:
          // redirect to not-found page
          break;
        default:
          // show generic error notification
      }
      return throwError(() => error);
    })
  );
};
```

Register the interceptor in `app.config.ts`:

```typescript
export const appConfig: ApplicationConfig = {
  providers: [
    provideHttpClient(withInterceptors([errorInterceptor])),
    provideRouter(routes),
  ],
};
```

## Pagination

All list endpoints that return more than 20 results use server-side pagination.
Pass pagination params as query parameters:

```typescript
getUsers(page = 0, size = 20): Observable<PagedResponse<User>> {
  const params = new HttpParams()
    .set('page', page)
    .set('size', size)
    .set('sort', 'createdAt,desc');

  return this.http.get<PagedResponse<User>>(this.baseUrl, { params });
}
```

Standard paginated response interface:

```typescript
export interface PagedResponse<T> {
  content: T[];
  totalElements: number;
  totalPages: number;
  size: number;
  number: number;
  first: boolean;
  last: boolean;
}
```

## Loading and Error State

Every component that fetches data must handle three states explicitly — loading,
error, and success. Use Angular Signals and the `@if` control flow syntax:

```typescript
@Component({
  selector: 'app-user-list',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `
    @if (loading()) {
      <mat-spinner />
    } @else if (error()) {
      <app-error-message [message]="error()!" />
    } @else {
      @for (user of users(); track user.id) {
        <app-user-card [user]="user" />
      }
    }
  `,
})
export class UserListComponent {
  users = signal<User[]>([]);
  loading = signal(false);
  error = signal<string | null>(null);
}
```

Never leave a component without a loading indicator or error state.
````

## Common Issues

**Agent generates NgModule-based components**  
This means `architecture.md` is not being read. Recheck the inclusion front matter
and confirm the file is saved and in `.kiro/steering/`.

**Agent ignores steering files and uses its own defaults**  
Check the front matter — it must be `inclusion: always` (not `alwaysApply: true`).
Using the wrong key means the file is treated as `manual` inclusion and will not
load automatically.

**Test 2 fails — agent suggests `fixture.debugElement`**  
This means `testing-standards.md` is not being read. Recheck the file path and
front matter.

**I don't see a Steering panel — only a chat window**  
You are on the older Amazon Q Developer extension, not yet upgraded to Kiro. Use
`@workspace` in the chat panel instead (see Step 5). The steering files work
identically — only the UI for browsing them differs.
